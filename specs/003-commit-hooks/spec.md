# Feature Specification: Commit hooks and commit-message convention

**Feature Branch**: `003-commit-hooks`

**Created**: 2026-10-07

**Status**: Draft

**Input**: User description: "Implement GitHub issue #3 (https://github.com/jessiicamaru/task-management/issues/3): chore(tooling): husky, lint-staged and commitlint on Conventional Commits — husky via prepare so hooks install on npm ci; pre-commit runs lint-staged (*.js → eslint --fix + prettier --write; json/md/yml → prettier --write); commitlint extending config-conventional with a restricted scope list; commit-msg hook; docs/commits.md with three real examples and when --no-verify is acceptable. Acceptance: bad message rejected, feat(tasks): add status filter accepted, lint errors auto-fixed or blocked, fresh npm ci installs the hooks."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Commit messages follow the convention (Priority: P1)

A contributor writes a commit message. If it is not a Conventional Commit with a known scope, the
commit is refused with an explanation; if it is, it goes through.

**Why this priority**: The PR and issue skills derive titles, `type:` labels and badges from the
commit prefix; a drifting history turns every one of those into a guess.

**Independent Test**: `git commit -m "bad message"` → rejected; `git commit -m "feat(tasks): add status filter"` → accepted.

**Acceptance Scenarios**:

1. **Given** hooks are installed, **When** a commit message has no type, **Then** the commit is rejected with the convention's error.
2. **Given** hooks are installed, **When** the message is `feat(tasks): add status filter`, **Then** the commit succeeds.
3. **Given** a scope outside the agreed list, **When** committing, **Then** the commit is rejected and the error lists allowed scopes.

---

### User Story 2 - Lint problems caught before the push (Priority: P2)

Staged API files are linted and formatted at commit time: fixable problems are fixed and included
in the commit; unfixable ones block it.

**Independent Test**: Stage a file with misordered imports → commit succeeds with them fixed; stage
a file with `console.log` in a module → commit blocked.

**Acceptance Scenarios**:

1. **Given** a staged file with a fixable lint/format problem, **When** committing, **Then** the fix is applied and committed.
2. **Given** a staged file with an unfixable lint error, **When** committing, **Then** the commit is blocked.
3. **Given** only files outside `server/` are staged, **When** committing, **Then** no API tooling runs on them.

---

### User Story 3 - Hooks install themselves (Priority: P3)

A fresh `npm ci` in `server/` installs the hooks with no extra step.

**Independent Test**: Unset the hooks path, run `npm ci`, observe the hooks path set and hooks active.

### Edge Cases

- The repository is a monorepo: the git root is not `server/`. Hooks must work from the git root and from worktrees.
- `npm ci` in an environment without git (Docker build, #37) must not fail because hook installation cannot run.
- A legitimate emergency commit: bypass with `--no-verify` is documented, with when it is acceptable.
- A merge or revert commit message generated by git must still pass.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Hooks MUST be installed automatically by the `server/` package install (`prepare`).
- **FR-002**: A pre-commit hook MUST run staged-file linting: `*.js` → lint fix then format; `*.{json,md,yml,yaml}` → format (respecting the format ignore list).
- **FR-003**: A commit-msg hook MUST validate the message against Conventional Commits.
- **FR-004**: Scopes MUST be restricted (error, not warning) to the agreed list; a scope is optional.
- **FR-005**: `docs/commits.md` MUST show three real examples, the allowed scopes, and when `--no-verify` is acceptable.
- **FR-006**: Installation MUST NOT fail where there is no git repository.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of the four acceptance checks in issue #3 pass.
- **SC-002**: Pre-commit adds no more than a few seconds on a typical commit (no test run in the hook).
- **SC-003**: Every scope used by the existing backlog titles is accepted (0 backlog titles rejected).

## Assumptions

- **Scope list** is the union of the 15 scopes the `gh-issue-create` / `gh-pr-create` skills name
  (`api auth users projects tasks db config health web ui docker ci deploy docs test`) and the
  scopes the backlog titles and workflow already use (`tooling repo obs e2e quality setup specs`).
  The issue's 13-scope list omits `web` (13 backlog titles) and `tooling` (this issue's own title);
  enforcing it verbatim would reject the backlog's own commits.
- Scope enforcement is **strict** (error). A change spanning areas takes the domain scope, as the PR skill already says.
- Pre-commit does **not** run tests (issue recommendation).
- Hooks live in `server/.husky/`; `web/` (#51) can extend the same hooks later.
- `lint-staged` is pinned to **major 16**: v17 requires Node ≥ 22.22.1, above the project floor of 22.12.
